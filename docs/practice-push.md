# Practice notifications and background calendar sync

## Behavior

Every committed practice creation, time/date change, location change (including clearing it), and cancellation queues an alert for all registered band-member devices, including the leader. Location changes use **Practice Location Changed** and say the practice location was changed. A simultaneous time/location change says both changed. Default band-location edits only affect future practices and do not notify about existing practices. Calendar-event-ID bookkeeping and unchanged saves do not notify.

Alerts request background execution with `content-available: 1`. The app fetches current authorized practice data for all joined bands, updates existing EventKit events, and reconciles cancellations. It never trusts practice details from a push payload and never requests calendar access in the background. This runs independently of calendar-based/manual availability, selected band, and navigation. Existing periodic background refresh and app activation also attempt reconciliation.

APNs/iOS controls alert presentation and background execution. Notification permission, calendar permission, connectivity, Background App Refresh, power management, and force-quitting affect results. APNs acceptance does not establish a delivered notification or an updated calendar. Opening the app remains a fallback. Duplicate Realtime/local practice alerts are removed; member-joined local notifications retain their previous behavior.

## Reused pattern

Adapted from TV & Movie's `SocialPushNotificationDelegate.swift`, guarded registration RPCs in `20260920222123_social_push_notifications.sql`, `_shared/apns.ts`, and its isolated invite-acceptance test. The APNs helper retains its ES256/PKCS8 signing and sandbox/production topic handling; Band Practice adds cached provider JWTs, bounded requests, stable retry IDs, expiration, and background-refresh payloads.

The shared app guide is [iOS push notifications](/Users/keithbarney/Documents/Github/agent-guides/ios-push-notifications.md). It documents the baseline, gaps found in the source implementation, and the stronger queue/account-boundary pattern introduced here. This task does not migrate TV & Movie's implementation.

## Rollout

1. Enable Apple's Push Notifications capability for `com.keithbarney.heavybandmanager` and `.local`, and regenerate matching provisioning profiles. Debug expects development/sandbox; App Store Release expects production. Never substitute a mismatched profile or remove the entitlement to hide a signing failure.
2. Apply `supabase/migrations/20260930160000_practice_push_notifications.sql` after local/CI database checks. It enables RLS with no client table access; clients can only call guarded register/unregister RPCs. Service-role workers can lease and complete jobs. The trigger captures notifications in the practice transaction.
3. Set the function secrets `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY`, and a fresh random `PRACTICE_PUSH_WORKER_SECRET`. Use the existing Apple key only if its authorization includes these bundle IDs; topic-restricted keys may need a separate key. Reuse the TV & Movie secret **names and setup**, without printing/copying its secrets into source. Supabase supplies `SUPABASE_URL` and its service-role/modern secret keys.
4. Deploy `practice-push` with JWT verification disabled as specified in `config.toml`. Its own `x-practice-push-secret` authentication is mandatory. No client can invoke the worker using a user JWT. Do not expose the worker secret or APNs key in the iOS app.
5. In Supabase Vault, create `practice_push_project_url` and `practice_push_worker_secret` (the latter matching the function secret). Apply `supabase/rollouts/enable_practice_push_worker.sql`. It wakes the worker after enqueue, retries every minute, and removes jobs after seven days. It preserves the practice save if the HTTP wakeup fails.
6. Install the signed compatible app on isolated authorized test devices. Registration happens after authenticated launch/foreground and retries after failures. Existing notification prompts/Settings remain the permission entry points. Sign-out unregisters before revoking the session; a failure is shown and leaves the account signed in for retry. Account deletion unregisters first, then the auth-user cascade removes remaining devices/jobs.

No old practices generate alerts on migration. Devices must register before future edits can enqueue alerts. Multiple installed Debug/Release apps are separate destinations. The sender rechecks membership, token, and account ownership immediately before sending, deletes invalid tokens conditionally, and retries transport/provider failures. A notification already accepted by APNs cannot be recalled by sign-out. Job leases prevent overlapping workers; stable APNs collapse IDs reduce retries producing duplicate visible alerts, but delivery is not exactly-once.
