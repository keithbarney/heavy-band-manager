# Reliability fixes — 2026-09-15

## Availability transactions

Calendar-derived availability, weekly rules, availability mode, and the practice window now share a monotonically increasing `band_members.availability_revision`. Current app writers send the revision they read. PostgreSQL locks the member row, verifies the signed-in member and expected revision, and performs each multi-row replacement in one transaction.

`replace_calendar_availability` returns `NULL` without changing slots when the mode or revision is stale. A successful replacement advances the revision, which also prevents an older automatic refresh from overwriting a newer automatic refresh. Weekly rules, projected dated slots, mode, setup status, and revision commit together through `save_weekly_availability`. Mode and practice-window changes use their own revision-checked functions. All functions are `SECURITY INVOKER`; existing RLS remains in force, and execute access is limited to `authenticated`.

The foreground client immediately applies the revision returned by each successful function while the same account and band remain selected. A later member-list reload cannot be the only source of that revision. Foreground and background automatic refreshes now use the same replacement function. A stale background result fails the refresh and does not advance the local last-sync timestamp.

The migration was deployed to the Band Practice Supabase project on September 15, 2026 at 15:26 UTC, with all 30 maintained database contract assertions passing against its real RLS and grants. The local filename matches the recorded remote version:

`supabase/migrations/20260915152617_harden_availability_and_practices.sql`

Older deployed clients still have direct RLS-authorized access to availability tables. They do not participate in the revision contract and can bypass it until upgraded. The migration deliberately does not use `SECURITY DEFINER` or weaken RLS to block those clients.

## Practice mutation behavior

Schedule and cancel now throw backend errors to the day sheet. The sheet stays open, shows a retry action, and only shows a success toast and dismisses after a returned database mutation. Local widget and calendar side effects recheck the captured account and band after the server response.

The Schedule button is disabled while a mutation is running, exact already-scheduled windows are removed from Best Windows, and PostgreSQL enforces one practice per `(band_id, date, start_minutes, end_minutes)`. If a concurrent or ambiguous request encounters the uniqueness rule, the app refreshes the schedule and reports that the practice already exists without presenting it as a new success.

The uniqueness migration never deletes existing practices. Run this preflight before deployment:

```sql
select
  band_id,
  date,
  start_minutes,
  end_minutes,
  count(*) as practice_count,
  array_agg(id order by scheduled_at, id) as practice_ids
from public.scheduled_practices
group by band_id, date, start_minutes, end_minutes
having count(*) > 1
order by date, start_minutes;
```

If rows are returned, an organizer must decide which record in each group is authoritative before the migration is applied. The migration stops with the duplicate-group count and this remediation hint instead of removing data.

## Practice calendar refresh feedback

Practice-event reconciliation returns attempted, restored, failed, and stale-cleanup results. Settings shows a success message for a complete refresh and a retryable alert for partial or total failure. Per-practice failures continue through the batch so a partial result states how many events were restored.

## Isolated mock behavior

The opt-in Simulator mock now keeps profile name, instrument, avatar, band logo, leave-band, delete-band, schedule, and cancel mutations in memory. Avatar and logo uploads validate and cache the supplied image bytes in a Debug-only image store, and the existing artwork views render those cached images. Failure scenarios preserve the previous availability and practice state. The mock Supabase endpoint remains the localhost fallback, and mock paths do not write to Supabase, EventKit, notifications, email, or personal storage.

## Calendar permission policy

Manual availability still requires Calendar access. This preserves the current production behavior and the older onboarding requirement that confirmed practices be added to Calendar. It conflicts with the later weekly-availability note that manual users should not be prompted unless they opt into calendar additions. No permission behavior changed until the product requirement has one authoritative answer.
